# GameCoin v0.9.0 Mainnet Candidate

This branch is the consensus-hardening line that must be proven on a candidate testnet before any mainnet genesis is created.

## Candidate rules introduced so far

### Integer chainwork

Cumulative proof-of-work is represented with Python integers only. For a proof-of-work target `T`, block work is:

`floor(2^256 / (T + 1))`

Legacy leading-zero blocks use the mathematically equivalent exact work value `16^N` for `N` required leading hexadecimal zeroes.

Fork choice will ultimately compare the cumulative integer work of fully validated candidate chains. Seed identity must not override cumulative proof-of-work.

### Block timestamps

The candidate timestamp policy uses:

- an 11-block median-time-past window
- a requirement that a new block timestamp be strictly greater than median time past
- a maximum future timestamp of two hours beyond the validating node's current time

Difficulty timing still needs to be migrated to hardened timestamp samples before this rule is considered fully integrated.

### Coinbase maturity

Candidate coinbase outputs require **100 blocks of maturity**. A reward created at height `H` may first be spent in block `H + 100`. Mempool validation uses the next candidate block height when deciding whether a reward is spendable.

The candidate UTXO model records coinbase origin and creation height so the rule can be applied deterministically.

### Transaction fees

Fees use the UTXO convention:

`fee = sum(inputs) - sum(outputs)`

Outputs may not exceed inputs. Zero-fee transactions remain consensus-valid at this stage; the default candidate wallet policy is **0.001 GAME (100,000 atoms)**.

A candidate miner must claim exactly `block subsidy + all included transaction fees` in the block coinbase. This replaces the v0.8.x behavior where an input/output difference could disappear instead of being paid to the miner.

## Candidate-network requirement

Coinbase maturity and miner fee collection are hard-fork rules. They are not safe to activate retroactively on the current `gamecoin-public-testnet-v2` history. Before v0.9.0 is deployed, we should create a separate candidate testnet/network genesis (planned as the next testnet generation) and run the hardening build there.

The current live v0.8.3 public-testnet-v2 seed and wallets should remain unchanged until that candidate network is ready.

## Test status

Deterministic tests cover integer work arithmetic, legacy work conversion, cumulative chainwork, median-time-past, the future-time boundary, the 100-block coinbase maturity boundary, implicit fee arithmetic, invalid overspending, zero-fee validity, and subsidy-plus-fee coinbase accounting.

Local integration tests additionally exercise immature coinbase rejection, mature coinbase spending, miner template fee collection, and block rejection when the coinbase fails to claim the required fees. Full node/reorg integration and candidate-network soak tests remain required.
